# Audit complet — Coffre 0.8.0

**Date :** 7 novembre 2026  
**Périmètre :** application web/PWA, extension Chromium, coque desktop Tauri, cœur de coffre TypeScript, documentation, CI et chaîne de build.  
**Version auditée :** 0.8.0 (`package.json`, `src-tauri/Cargo.toml`, `tauri.conf.json`).  
**État Git :** aucun commit (identité Git absente) ; l’audit porte sur l’arbre de travail stagé.

> **Nature de l’audit.** Audit statique et dynamique mené localement : lecture intégrale
> du code applicatif, exécution des tests, builds, analyse des dépendances,
> vérification de signatures et tests UI. Ce n’est **pas** un audit cryptographique
> externe, ni un test d’intrusion, ni une revue juridique.

> **Mise à jour post-audit.** Les statuts du tableau ci-dessous et la section 10
> reflètent l’état après les corrections. Les sections détaillées décrivent le

## 1. Synthèse exécutive

**Note globale : 7,6 / 10.**

Le socle cryptographique et la discipline de format sont solides : hiérarchie de
clés claire, AAD dédiées, AES-256-GCM, Argon2id, validation Zod, import borné,
CSP stricte, aucune requête réseau, sauvegardes et récupération optionnelle. Les
tests sont nombreux et les builds principaux passent.

Les risques restants sont surtout **périphériques** : distribution macOS non
notarisée, expérience Touch ID adossée au trousseau classique (double dialogue,
autorisation « Always Allow » fragile), absence d’intégration AutoFill native,
déni de service possible via des paramètres KDF extrêmes, absence de `strict`
TypeScript, et quelques angles morts de CI (Rust, extension, desktop, mobile).

Un défaut **critique** a été trouvé et corrigé pendant l’audit :

> **A-01 — Effacement de la clé maîtresse de session après un déverrouillage
> par trousseau ou Touch ID.** `openVaultFileWithMasterKey()` conservait la
> référence au tampon fourni par l’appelant ; le `wipe()` du `finally` effaçait
> donc la clé de la session. Les opérations suivantes (ajout de coffre, activation
> de la récupération, changement de mot de passe) échouaient ou scellaient des
> clés avec une clé nulle. Corrigé par clonage dans `VaultSession`, avec test de
> régression (164 tests unitaires).

## 4. Constats détaillés

### A-01 — P0 — Clé maîtresse effacée après déverrouillage rapide

**Fichiers :** `src/lib/vault.ts`, `src/state/VaultProvider.tsx`.

`openVaultFileWithMasterKey(file, masterKey)` faisait :

```ts
const session = new VaultSession(masterKey)
```

Le provider, après un déverrouillage par trousseau ou Touch ID, faisait :

```ts
const masterKey = fromBase64(secret)
try {
  const opened = await openVaultFileWithMasterKey(file, masterKey)
  // …
} finally {
  wipe(masterKey)
}
```

La session et l’appelant partageaient le même `Uint8Array` : le `wipe()` du
`finally` mettait à zéro la clé maîtresse de la session. Conséquences :

- `changePassword` échouait ensuite avec « mot de passe actuel incorrect » ;
- `addVault` scellait la clé du nouveau coffre avec une clé nulle ;
- `enableRecovery` scellait le `guard` avec une clé nulle ;
- selon le chemin, le coffre pouvait devenir partiellement incohérent.

**Correction appliquée :** `new VaultSession(masterKey.slice())`. L’appelant
reste propriétaire de son tampon ; `unlockVaultFile` et `recoverVaultFile`
effacent leur copie après l’appel. Test de régression ajouté :

```ts
it('conserve la clé de session après effacement du tampon d’entrée', …)
```

Le test vérifie que la session reste utilisable après `wipe(input)` et qu’un
second coffre ajouté puis rouvert fonctionne.

**Statut : corrigé, couvert par les 164 tests.**

### A-02 — P1 — Distribution macOS non notariée et « Always Allow » fragile

**Fichiers :** `src-tauri/tauri.conf.json`, `src-tauri/src/lib.rs`.

Le bundle est signé **ad hoc** (`signingIdentity: "-"`, identifiant
`app.coffre.desktop`) et n’est pas notarié. `codesign --verify --deep --strict`
passe, mais :

- Gatekeeper affiche un avertissement au premier lancement ;
- l’autorisation « Always Allow » du trousseau est liée à la signature ; une
  signature ad hoc dépend du contenu du binaire, donc une recompilation peut
  redemander l’autorisation ;
- des utilisateurs peuvent refuser le DMG non notarié.

Le prompt observé (`app.coffre.desktop.biometric`) est le dialogue ACL du
trousseau de login, distinct de Touch ID.

**Recommandations :**

1. Signer avec un certificat **Developer ID Application** stable.
2. Activer `hardenedRuntime` en distribution.
3. Notariser avec `notarytool`, agrafer le ticket et vérifier avec `spctl`.
4. Documenter le parcours « clic droit → Ouvrir » pour les builds locaux.
5. Éviter les rebuilds entre deux autorisations « Always Allow ».

**Statut : ouvert.** La signature ad hoc et l’identifiant stable sont déjà un
progrès par rapport à un binaire non signé ; ce n’est pas une signature de
distribution.

### A-03 — P1 — Déni de service par paramètres KDF extrêmes

**Fichier :** `src/lib/vault.ts`, schéma `kdfSchema`.

Le schéma accepte :

```ts
memoryKiB: z.number().int().min(8_192).max(1_048_576) // jusqu’à 1 Gio
iterations: z.number().int().min(1).max(10)
parallelism: z.number().int().min(1).max(16)
```

Un fichier `.coffre` importé ou restauré peut donc demander **1 Gio de mémoire
et 10 passes Argon2id**, sans que l’utilisateur puisse annuler. Sur une machine
modeste, cela provoque un gel, un swap massif ou un `OutOfMemory`.

**Recommandations :**

- plafonner à 256 Mio, 6 itérations et 8 threads pour l’import ;
- avertir si les paramètres diffèrent des valeurs par défaut ;
- dériver dans un Web Worker avec possibilité d’annuler ;
- conserver la lecture des anciens fichiers aux paramètres faibles, avec un
  avertissement de sécurité.

**Statut : ouvert.** C’est le principal risque de disponibilité restant.

### A-04 — P1 — Modèle Touch ID et trousseau classique

**Fichiers :** `src-tauri/src/lib.rs`, `src/lib/biometrics.ts`,
`src/state/VaultProvider.tsx`, `docs/SECURITY.md`.

Le flux actuel :

1. la clé maîtresse est stockée en base64 dans le service
   `app.coffre.desktop.biometric` ;
2. `biometric_load` exécute `LocalAuthentication` ;
3. après succès, `keyring` lit l’entrée du **trousseau de login** ;
4. macOS peut afficher un second dialogue ACL pour autoriser la lecture.

Points forts :

- service biométrique séparé, donc `keychain_load` ne peut pas lire la clé ;
- l’authentification est faite **dans la commande Rust**, pas seulement dans
  l’UI ;
- la clé n’est pas réécrite à chaque déverrouillage depuis la correction du
  cache `biometricKeyFileRef` ;
- une clé périmée est supprimée.

Limites :

- Touch ID est une barrière **applicative** ; l’entrée du trousseau n’est pas
  protégée par `SecAccessControl`/Secure Enclave ;
- un processus avec les droits de l’utilisateur peut tenter de lire l’entrée
  selon l’ACL du trousseau ;
- double dialogue possible (Touch ID puis mot de passe du trousseau) ;
- « Always Allow » peut être oublié après un nouveau build ad hoc.

**Recommandations :**

- à terme, créer un élément `kSecClassGenericPassword` avec
  `kSecAttrAccessControl` (`kSecAccessControlBiometryCurrentSet`) et un Keychain
  Access Group, ou une clé Secure Enclave qui chiffre la clé maîtresse ;
- sinon, documenter clairement que Touch ID protège l’usage applicatif, pas
  l’accès OS au trousseau ;
- proposer un bouton « Réinitialiser Touch ID » qui supprime l’entrée et la
  recrée après un changement de signature.

**Statut : ouvert, documenté.** Le compromis est acceptable pour un projet local
non audité, mais doit être explicite pour une distribution large.

### A-05 — P1 — Navigation externe de la WebView Tauri

**Fichiers :** `src-tauri/src/lib.rs`, `src/components/ItemDialog.tsx`.

Les URL d’éléments sont rendues avec :

```tsx
<a href={target} target="_blank" rel="noreferrer noopener">
```

`target` est validé par `safeExternalUrl` (http/https uniquement), mais la coque
Tauri ne définit aucun `on_navigation` ni gestionnaire de nouvelle fenêtre. Selon
le comportement de wry/macOS, un clic peut :

- ouvrir le navigateur système (souhaitable), ou
- créer une nouvelle WebView / naviguer dans la WebView de l’application
  (indésirable : contenu distant dans la coque, phishing, perte de la CSP
  locale).

**Recommandations :**

- ajouter un `on_navigation` Rust qui n’autorise que l’origine locale et ouvre
  les URL externes via `tauri-plugin-opener` (ou l’API système) ;
- ajouter un test manuel documenté : clic sur un lien d’élément dans le desktop ;
- vérifier également le comportement de `window.open` et des liens `mailto:`
  (refusés par `safeExternalUrl`).

**Statut : à vérifier / à corriger avant diffusion desktop.**

### A-06 — P2 — TypeScript non strict

**Fichiers :** `tsconfig.app.json`, `tsconfig.extension.json`,
`tsconfig.node.json`.

Aucun des trois tsconfig n’active :

- `strict`;
- `strictNullChecks`;
- `noImplicitAny`;
- `exactOptionalPropertyTypes`;
- `noUncheckedIndexedAccess`.

Le code compile, mais l’absence de `strictNullChecks` et `noImplicitAny` laisse
passer des erreurs de type que TypeScript aurait dû signaler, en particulier
autour des valeurs optionnelles de coffre, des retours de `parseVaultFile` et des
callbacks d’import.

**Recommandation :** activer `strict` progressivement (commencer par
`strictNullChecks` + `noImplicitAny`), corriger les erreurs, puis ajouter
`noUncheckedIndexedAccess` sur `src/lib`. Ajouter un job CI qui échoue si
`strict` est désactivé.

**Statut : ouvert.**

### A-07 — P2 — Concurrence multi-instance et multi-onglets

**Fichiers :** `src-tauri/src/lib.rs`, `src/lib/storage.ts`,
`src/state/VaultProvider.tsx`.

- Aucun `tauri-plugin-single-instance` : deux instances desktop peuvent ouvrir
  le même profil de WebView et écrire le même coffre.
- Plusieurs onglets web peuvent déverrouiller le même coffre ; les écritures
  IndexedDB sont sérialisées par transaction, mais les rotations de sauvegarde et
  les états React divergent.
- `beforeunload`/`pagehide` verrouillent la session de l’onglet, pas les autres.

**Recommandations :**

- ajouter `tauri-plugin-single-instance` et activer la fenêtre existante ;
- ajouter un verrou `navigator.locks` ou un `BroadcastChannel` pour signaler
  qu’un autre onglet est déverrouillé, et verrouiller les autres onglets ;
- documenter que le coffre doit être utilisé dans un seul onglet.

**Statut : ouvert.**

### A-08 — P2 — Vérification d’intégrité incomplète pour la récupération

**Fichier :** `src/lib/vault.ts`, `verifyVaultFile`.

La vérification couvre les coffres, éléments, versions et pièces jointes, mais
pas l’enveloppe `recovery` :

- `recovery.guard` n’est pas déchiffré ;
- les `wraps` ne sont pas ouverts avec la clé de récupération ;
- une enveloppe corrompue peut donc passer « Intégrité confirmée » alors que la
  phrase de récupération ne fonctionne plus.

**Recommandation :** vérifier `guard` avec la clé maîtresse de session et chaque
`wrap` avec la clé de récupération en mémoire ; signaler les incohérences.

**Statut : ouvert.**

### A-09 — P2 — Intégrité globale et anti-rétrogradation

Chaque enregistrement est authentifié par AES-GCM, mais le **fichier dans son
ensemble** ne possède pas de MAC/signature. Un attaquant qui peut écrire le
fichier peut :

- supprimer proprement un élément et ses pièces jointes/versions (la
  vérification passe) ;
- supprimer une pièce jointe référencée (la vérification échoue, mais l’UI
  ouvre le reste) ;
- remplacer le fichier par une version antérieure complète (rollback) ;
- modifier des métadonnées non chiffrées (`createdAt`, `updatedAt`, nombre
  d’éléments visibles, identifiants) tant que les AAD restent cohérentes.

La confidentialité reste assurée ; l’intégrité et la fraîcheur ne le sont pas.

**Recommandations :**

- documenter explicitement cette limite dans `docs/SECURITY.md` (déjà partielle) ;
- option : ajouter un manifeste chiffré/signé (HMAC avec une clé dérivée) ou une
  signature Ed25519 de l’appareil ;
- au minimum, détecter les suppressions inattendues par un compteur/HMAC.

**Statut : ouvert, limite de conception.**

### A-10 — P2 — Presse-papiers de l’extension non effacé

**Fichier :** `extension/popup.ts`.

`copyPassword` et `copyTotp` appellent directement
`navigator.clipboard.writeText(...)`, sans le délai d’effacement de
`src/lib/clipboard.ts`. Le mot de passe ou le code TOTP reste dans le
presse-papiers jusqu’à ce que l’utilisateur le remplace.

**Recommandations :**

- réutiliser un mécanisme d’effacement (alarmes + document offscreen, ou demander
  à l’onglet Coffre d’effectuer la copie avec `copySensitive`) ;
- au minimum, avertir dans l’UI et documenter la limite.

**Statut : ouvert.**

---

### A-11 — P2 — Toutes les connexions affichées quand le site ne correspond pas

**Fichier :** `extension/popup.ts`, `loadResults`.

Si la recherche par hôte ne renvoie rien, le popup relance une recherche vide et
affiche **toutes** les connexions du coffre, avec un texte « Aucun identifiant
pour ce site. Toutes vos connexions : ». Sur un site de phishing sans
correspondance, l’utilisateur peut être incité à choisir un identifiant et à le
remplir.

**Recommandations :**

- ne jamais remplir automatiquement dans ce cas ;
- afficher les autres connexions uniquement après une action explicite
  (« Voir toutes mes connexions ») ;
- afficher un avertissement de domaine.

**Statut : ouvert.**

### A-12 — P2 — Passerelle `window.__coffreExtension`

**Fichiers :** `src/components/ExtensionBridge.tsx`,
`docs/SECURITY.md`.

La passerelle expose `search` et `fill` sur `window` dans le monde principal de
la page. Tout script exécuté dans l’onglet Coffre pendant qu’il est déverrouillé
peut appeler `fill()` et lire un mot de passe. La CSP limite les scripts
distants, mais pas une extension malveillante ni un XSS.

**Recommandations :**

- rendre la passerelle moins large (ne pas exposer `fill` plus longtemps que
  nécessaire, effacer après usage) ;
- ou passer par un canal `postMessage` avec un jeton par session et vérifier
  `event.source` ;
- documenter le risque (déjà partiellement dans `docs/SECURITY.md`).

**Statut : documenté, conception à durcir.**

### A-13 — P2 — Effacement incomplet de la clé d’élément

**Fichier :** `src/lib/vault.ts`, `openVaultFileWithMasterKey`.

```ts
const itemKey = await openBytes(record.key, vaultKey, itemKeyAad(…))
const content = await openJson(record.content, itemKey, itemContentAad(…))
wipe(itemKey)
```

Si `openJson` ou `itemContentSchema.parse` lève, `itemKey` n’est pas effacé. Le
même schéma existe pour la clé de coffre si sa longueur est invalide. Les autres
fonctions (`updateItem`, `trashItem`, `openAttachment`, etc.) utilisent un
`finally` correct.

**Recommandation :** envelopper l’ouverture dans `try/finally` et effacer
`itemKey` dans tous les cas.

**Statut : ouvert.**

### A-14 — P2 — Performance du déverrouillage et des grandes listes

- Argon2id (64 Mio, 3 passes, 4 threads) est exécuté sur le fil principal par
  `hash-wasm` ; l’UI peut geler pendant la dérivation.
- `openVaultFileWithMasterKey` déchiffre tous les éléments avant d’afficher
  l’interface ; un fichier de 20 000 éléments peut bloquer plusieurs secondes.
- La liste rend tous les éléments filtrés sans virtualisation ni pagination.
- `searchableText` reconstruit une chaîne pour chaque élément à chaque frappe.
- La vérification d’intégrité déchiffre toutes les versions/pièces jointes sur
  le fil principal.

**Recommandations :** Web Worker pour Argon2 et le déchiffrement initial ;
virtualisation de la liste ; index de recherche pré-calculé ; indicateur de
progression annulable.

**Statut : ouvert.**

---

### A-15 — P2 — Amplification du stockage

Chaque mutation réécrit le fichier complet et fait tourner trois sauvegardes
complètes. Avec 50 Mio de pièces jointes, une modification peut écrire ~200 Mio
dans IndexedDB. Sur un appareil mobile ou un quota serré, cela peut provoquer
des échecs ou une éviction.

**Recommandations :** limiter la taille totale, stocker les pièces jointes dans
des enregistrements séparés (ou un magasin dédié), ne sauvegarder que les
métadonnées modifiées, ou documenter la limite.

**Statut : ouvert.**

### A-16 — P2 — CI incomplète

Points positifs : lint, typecheck, tests, build PWA, build extension, E2E
Chromium/WebKit, audit npm, build desktop sur macOS/Linux/Windows (hors PR),
artefacts, Dependabot.

Manques :

- `cargo test`, `cargo clippy`, `cargo fmt --check` et `cargo audit` ;
- `extension:smoke` (test d’intégration réel de l’extension) ;
- tests desktop Tauri (au moins lancement et smoke) ;
- tests mobile (aucun SDK) ;
- pas de vérification de la cohérence des versions
  (`package.json` vs `tauri.conf.json` vs manifeste d’extension) ;
- pas de test de la page d’authentification à 900 px (régression corrigée) ;
- pas de test de la présence de `robots.txt`/`noindex` ;
- pas de SBOM ni de provenance de build.

**Recommandations :** ajouter les jobs Rust (tests + clippy + fmt), un smoke
extension dans la CI, un test de taille de page d’authentification, et un script
`version:check`.

**Statut : ouvert.**

### A-17 — P2 — Capacités Tauri trop larges

**Fichier :** `src-tauri/capabilities/default.json`.

La capability accorde `core:default`, qui inclut les permissions par défaut de
`path`, `event`, `window`, `webview`, `app`, `image`, `resources`, `menu` et
`tray`. L’application n’utilise que :

- `core:window:allow-start-dragging` ;
- les commandes applicatives de trousseau/biométrie.

Les commandes applicatives sont, par défaut, accessibles à toutes les WebViews
Tauri. Un contenu compromis pourrait appeler `keychain_load`/`keychain_delete`
et les commandes biométriques (la lecture biométrique exige toujours Touch ID).

**Recommandations :**

- réduire la capability à `core:window:allow-start-dragging` (tester le
  lancement) ;
- utiliser `tauri_build::AppManifest` pour déclarer et restreindre les commandes
  applicatives ;
- documenter les commandes exposées (déjà fait dans `docs/SECURITY.md`).

**Statut : ouvert.**

### A-18 — P2 — AutoFill système et mobile

`docs/MACOS-AUTOFILL.md` décrit correctement l’extension AutoFill native, mais
aucun code n’est présent. Le mobile n’est pas initialisé. C’est un choix de

### A-19 — P2 — Défilement de la page de connexion (corrigé)

La mise en page compacte ne s’appliquait qu’en dessous de 860 px de haut. À
900 px, la page mesurait 987 px → barre de défilement, alors que la fenêtre
Tauri par défaut fait 800 px et que l’utilisateur peut l’agrandir. Le seuil a été
porté à **1000 px**. Vérifié : `scrollHeight === innerHeight` à 800, 900 et
1000 px, avec et sans classe Tauri. En dessous de 700 px, la page défile
intérieurement pour rester accessible (limite de sécurité).

**Statut : corrigé.**

### A-20 — P2 — Changement de favori et historique (corrigé)

`updateItem` comparait `JSON.stringify(previous)` et `JSON.stringify(content)`,
ce qui incluait `favorite`. Un simple clic sur l’étoile créait donc une version,
contrairement à la documentation et au texte de l’historique. Une empreinte
`versionFingerprint` ignore désormais `favorite` pour décider de créer une
version ; le favori est toujours enregistré dans le contenu courant. Test ajouté :
« ne crée pas de version pour un simple changement de favori ».

**Statut : corrigé.**

### A-21 — P2 — Clé biométrique périmée après restauration/récupération

`biometricKeyFileRef` évite les réécritures de trousseau. Mais après une
restauration de sauvegarde ou une récupération par phrase **avec le même
`file.id`**, le cache peut considérer la clé comme déjà stockée alors que le mot
de passe maître a changé. Le prochain essai Touch ID échoue, supprime la clé, et
l’utilisateur doit passer par le mot de passe. C’est récupérable, mais l’UX est
trompeuse.

**Recommandation :** forcer `rememberBiometricKey(..., true)` après
`restoreFromBackup`, `recoverWithPhrase` et un `importVault` réutilisant le même
identifiant.

**Statut : ouvert.**

## 5. Ce qui est solide

### 5.1 Cryptographie et format

- Argon2id 64 Mio / 3 passes / 4 threads, sel de 16 octets, clé de 32 octets.
- AES-256-GCM, nonce aléatoire de 12 octets, tag de 128 bits.
- AAD de domaine pour chaque usage : coffre, méta, élément, contenu, version,
  pièce jointe, récupération.
- Hiérarchie claire : mot de passe → clé maîtresse → clé de coffre → clé
  d’élément → contenu/versions/pièces jointes.
- Changement de mot de passe sans réchiffrer les éléments.
- Enveloppe de récupération séparée (phrase EFF 10 mots, ~129 bits).
- Validation Zod stricte des fichiers et des contenus.
- Import limité (5 000 éléments, 20 Mo ; 50 Mo pour `.1pux`), attachements limités (5 Mio/pièce,
  25 Mio/élément, 50 Mio/coffre), versions plafonnées (20/élément,
  2 000/coffre).
- Aucune donnée en clair sur disque ; aucune clé dans IndexedDB.
- Effacement best-effort des tampons et des clés en mémoire.

### 5.2 Sécurité applicative

- Aucun `fetch`, XHR, WebSocket ou télémétrie dans le code livré.
- CSP stricte (web et Tauri), `freezePrototype`, `object-src none`,
  `base-uri none`, `form-action none`, `frame-ancestors none`.
- `safeExternalUrl` n’autorise que http/https et est couvert par des tests.
- React échappe les contenus ; aucun `dangerouslySetInnerHTML`.
- Modales avec piège à focus, `inert` sur la racine, restauration du focus.
- Verrouillage automatique, verrouillage à la perte de visibilité, `pagehide`.
- Trois générations de sauvegarde locale et vérification d’intégrité.
- Extension sans stockage de secret ; passerelle supprimée au verrouillage.

### 5.3 Desktop

- Tauri v2, CSP stricte, `freezePrototype`.
- `keyring` avec backend natif par OS.
- Commandes biométriques séparées et authentification dans Rust.
- Signature ad hoc valide, identifiant stable `app.coffre.desktop`.
- Fenêtre sans barre de titre macOS, feux de circulation en surcouche, zone de
  glissement.
- Build macOS reproductible localement, DMG généré.

### 5.4 Tests et documentation

- 164 tests unitaires, dont import (890 lignes de tests), vault (774 lignes),
  stockage natif et migration IndexedDB,
  crypto, recovery, storage, TOTP, générateur, extension, fixtures.
- 28 parcours E2E Chromium + WebKit, dont sécurité, import, récupération,
  corbeille, visibilité, verrouillage.
- Tests Rust de disponibilité Touch ID.
- Documentation très complète : SECURITY, PROTON-PASS, NATIVE, MACOS-AUTOFILL,
  README détaillé.
- Lighthouse accessibilité 1,0 après corrections.
- Smoke extension réussi avec la CSP de production.

## 6. Modèle de menace et risques résiduels

| Menace | Impact | État |
| --- | --- | --- |
| Mot de passe maître faible | Déchiffrement hors ligne | Argon2id, minimum 12 caractères, indicateur heuristique |
| Fichier `.coffre` volé | Brute force hors ligne | Argon2id 64 Mio ; phrase de récupération distincte |
| XSS / code dans la page | Vol des secrets pendant le déverrouillage | CSP stricte, pas de réseau, React escaping |
| Extension malveillante | Lecture du DOM/presse-papiers | Profil dédié recommandé, verrouillage après usage |
| Passerelle d’extension | Vol via `window.__coffreExtension` | Documenté ; à durcir |
| OS compromis / keylogger | Vol total | Hors périmètre |
| Trousseau macOS | Lecture par un processus utilisateur | ACL OS + Touch ID applicatif ; limite documentée |
| Fichier importé malveillant | DoS KDF, import partiel | Limites d’import ; KDF à plafonner |
| Suppression/rollback du fichier | Perte d’intégrité | Pas de MAC global ; à documenter/ajouter |
| Corruption du stockage | Perte du coffre | 3 sauvegardes, export, vérification |
| Perte du mot de passe | Perte définitive | Phrase de récupération optionnelle |
| Phrase de récupération compromise | Ouverture avec le fichier | Phrase non stockée, à conserver séparément |
| Dépendance compromise | Exécution arbitraire | Lockfile, audit high, Dependabot ; pas de SBOM |
| Build non signé | Distribution | Signature ad hoc ; Developer ID à faire |

## 9. Conclusion

Coffre 0.8.0 est un projet **sérieux et bien documenté**, avec un cœur
cryptographique cohérent et des tests utiles. Le défaut critique de gestion de
clé maîtresse a été corrigé, et plusieurs défauts d’interface, de contraste, de
version et de documentation ont été éliminés pendant l’audit.

Les prochains chantiers qui comptent vraiment sont :

1. **signature Developer ID + notarisation** ;
2. **plafonnement KDF et Web Worker** ;
3. **navigation externe Tauri maîtrisée** ;
4. **modèle Touch ID/trousseau assumé ou amélioré** ;
5. **`strict` TypeScript** ;
6. **intégrité globale/récupération vérifiée** ;
7. **CI Rust/extension/desktop/mobile**.

Tant que ces points ne sont pas traités, Coffre reste un excellent projet local
et expérimental, mais pas encore un gestionnaire de mots de passe de niveau
distribution grand public.

## Ajouts post-audit — stockage natif et export CSV

Le stockage desktop a été déplacé d’IndexedDB vers un fichier natif après

### Architecture

- `src-tauri/src/vault_store.rs` : lecture/écriture du fichier
  `app_data_dir()/vault/vault.coffre`, fichier temporaire, `flush`, `fsync`,
  renommage atomique, permissions `0600` sur les fichiers et `0700` sur le
  dossier (macOS/Linux), plafond de 100 Mo et écritures sérialisées par un
  mutex.
- Trois sauvegardes tournantes `vault.coffre.bak1` à `bak3`. À chaque écriture,
  `bak3` est supprimé, `bak2` devient `bak3`, `bak1` devient `bak2`, puis
  l’ancien courant devient `bak1`.
- Commandes Tauri : `vault_read`, `vault_write`, `vault_backup_read`,
  `vault_backup_write`, `vault_clear`. Aucune autre commande de stockage n’est
  exposée à la WebView.
- `src/lib/storage.ts` conserve deux backends : natif Tauri et IndexedDB Web.
  Au premier lancement desktop, si `vault_read` renvoie `null` et qu’un coffre
  IndexedDB existe, le coffre courant et ses sauvegardes sont écrits dans le
  stockage natif.
- `clearVaultStorage` supprime le stockage natif puis nettoie aussi IndexedDB,
  afin de ne pas laisser de copie résiduelle après une réinitialisation.
- L’interface Réglages affiche « Stockage natif » sur Tauri et conserve le
  statut de persistance du navigateur sur le Web.

### Export CSV

- `src/lib/export.ts` produit deux formats : `Mots de passe (Apple)` avec les
  six colonnes `Title,URL,Username,Password,Notes,OTPAuth` pour les connexions
  actives, et `Coffre complet` avec tous les types d’éléments, les champs
  personnalisés et les adresses multiples.
- Le CSV respecte RFC 4180 (guillemets doublés, champs multilignes), utilise
  UTF-8 sans BOM et des fins de ligne CRLF. Les éléments en corbeille sont
  exclus et les pièces jointes ne sont jamais incluses.
- `src/lib/import.ts` relit la colonne `coffre_custom_fields` pour le
  round-trip du format complet.
- Le fichier est en clair : l’interface et la documentation demandent de
  l’importer puis de le supprimer, et déconseillent de l’ouvrir dans un
  tableur (injection de formules).

### Vérifications

- `cargo test --lib` : 3 tests, dont la rotation complète des sauvegardes, la
  lecture/écriture et l’effacement.
- `src/lib/storage.native.test.ts` : 8 tests couvrant l’écriture native, les
  sauvegardes, la restauration, la migration IndexedDB, l’absence de
  re-migration, le nettoyage, un coffre IndexedDB illisible et les erreurs de
  format.
- `e2e/native-storage.spec.ts` : parcours complet Chromium + WebKit qui simule
  le runtime Tauri, migre un coffre IndexedDB, vérifie les sauvegardes, le
  rechargement natif et l’affichage « Stockage natif » dans les réglages.
- `src/lib/export.test.ts` et le parcours `e2e/import-export.spec.ts` couvrent
  l’export CSV Apple, l’export complet, l’échappement RFC 4180, le round-trip
  avec l’import et l’exclusion de la corbeille.
- `src/lib/security.test.ts` couvre l’analyse locale ; les parcours
  `e2e/security-dashboard.spec.ts`, `e2e/theme.spec.ts` et `e2e/bulk.spec.ts`
  couvrent le tableau de bord, les thèmes et les actions groupées.
- `src/lib/onePassword.test.ts` couvre l’import `.1pux` (connexions, cartes,
  notes, identités, champs personnalisés, archive et version future).
- `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` et
  `cargo audit` passent.
- Build desktop macOS arm64 relancé après l’ajout.

### Risques résiduels

- Le fichier et ses sauvegardes partagent le même compte et le même disque :
  un processus compromis du compte peut les lire ou les modifier. Le chiffrement
  et les permissions limitent l’exposition, pas un malware déjà actif.
- La migration ne supprime pas l’ancien coffre IndexedDB, qui reste une copie
  chiffrée de secours. Il est supprimé à la réinitialisation ou lors d’une
  future migration de nettoyage.
- La validation sur Windows/Linux et sur une installation signée reste à faire.
- L’AutoFill macOS nécessitera un App Group pour partager le fichier avec
  l’extension native ; ce n’est pas encore implémenté.
